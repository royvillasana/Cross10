## 1. Debts found while building, which is why they are here

- [ ] 1.1 **Audit the Croix10 capability specs against the Croix10 app.** Thirteen files and ninety-seven requirements went into `openspec/specs/` unchecked when C10 was archived at 110/219 tasks. Each is marked *not audited* at the top of its file; the audit either confirms a requirement, marks it pending like `shader-authoring` does, or removes it. Until then those specs state intent rather than behaviour
- [x] 1.2 **Undo writes into the wrong layer when the selection has moved.** *No longer destructive; still not fully correct, and the code says which. The sync now separates "the author moved a control" from "the runtime moved history" using the undo/redo stack depths, and refuses to fold when the reverted values belong to a layer other than the one selected. Undoing your own last edit on the layer you are looking at still works. Undoing an edit made on a layer you have since left is now inert rather than corrupting: the runtime reverted controls that no longer describe the layer the patch belonged to, and the product cannot be told which layer that was. The full fix remains the R56 amendment below.* Undoing an edit made while a *different* layer is selected reverts the control values and the sync folds them into whichever layer is selected now. A reverted patch does not say which layer it belonged to, and the record follows the controls (R56). Undo is correct for the layer you are on. The real fix is the record becoming the single store rather than a follower, which is an amendment to R56 rather than a patch to the sync
- [x] 1.3 **Forty-five acceptance rows name an automated test that does not exist.** *Done — it was sixty-one by the time it was measured, some of them added by this session's own rows. The reporter now lists none. Written as `studio-declarations.test.ts` (a control reaches the shader that draws it) and `studio-operations.test.ts` (the operations and the options a pipeline fixes) rather than as sixty-one stubs.* Measured with the delivery reporter (`vitest --reporter=./scripts/toolcraft-vitest-runtime-evidence-reporter.mjs`), which lists each one. Rows added in the last sessions match their tests; the backlog is older. The delivery gate in 2.x will fail on these once its authorization is resolved, so they are cheaper to clear before then than during
- [x] 1.4 **Five owners in `app-verification-impact.json` are rejected by the role classifier** — `app-acceptance-data.ts`, `app-acceptance.ts`, `app-identity.ts`, `app-performance.ts`, `studio-acceptance-rows.ts`. They are declaration modules the classifier does not count as production, and the inventory validator rejects an owner it does not recognise. Every *missing* owner has been registered; this is the other half, and it is the same 2.10 blocker (SS 2.10)
- [x] 1.5 **The performance gate `maps every product production module to current renderer pass ownership` fails as a symptom.** *Fixed, and the recorded cause was wrong. It does not fail "whenever any browser proof does" — it runs `playwright test --list` with the delivery-catalog reporter, which builds the catalog **without running a single proof** and throws on structural faults. Six were found and five fixed: a browser test named by a row and never written, two more named-but-absent, and three duplicate names where one test was doing several rows' work. The sixth was the one-acceptance-domain-per-file rule; `product-stack`, `product-media` and `product-timeline` now exist and the mixed files are split. Behind all of that sat 1.4: two stale acceptance ids, a module declared as a renderer-pass owner that owns no pass, and five declaration modules whose rows had to be reassigned to the code that implements them rather than to the file that declares them.* It derives its delivery catalog through Playwright, so it fails whenever any browser proof does. Worth re-checking once 1.3 and 1.4 are clear rather than treating it as a finding of its own
