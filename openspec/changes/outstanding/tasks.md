- [x] 1.2 **Undo writes into the wrong layer when the selection has moved.** *No longer destructive; still not fully correct, and the code says which. The sync now separates "the author moved a control" from "the runtime moved history" using the undo/redo stack depths, and refuses to fold when the reverted values belong to a layer other than the one selected. Undoing your own last edit on the layer you are looking at still works. Undoing an edit made on a layer you have since left is now inert rather than corrupting: the runtime reverted controls that no longer describe the layer the patch belonged to, and the product cannot be told which layer that was. The full fix remains the R56 amendment below.* Undoing an edit made while a *different* layer is selected reverts the control values and the sync folds them into whichever layer is selected now. A reverted patch does not say which layer it belonged to, and the record follows the controls (R56). Undo is correct for the layer you are on. The real fix is the record becoming the single store rather than a follower, which is an amendment to R56 rather than a patch to the sync

## 1a. Gaps the spec audit found

Each is a requirement the specs state and the app does not meet. They are listed
here as they are found, so 1.1 produces work rather than only verdicts.

- [x] 1a.1 **Difference and additive blend modes are missing** (`interference-layer`). The spec requires normal, multiply, screen, difference and additive; the app ships normal, multiply, screen and overlay. Two scenarios cannot pass: the absolute per-channel difference reading, and red-over-green rendering yellow. Additive in particular is not decoration — *Couleur Additive* is one of the techniques this product is named for, the gallery has entries claiming it, and the `stripe-engines` audit found that **Transchromie cannot be rendered as specified without it**: overlapping translucent planes with selectable subtractive *and additive* blending is what that technique is. *Built: both modes are in the shader and in the panel, and both spec scenarios are proved. The one anomaly turned out to be a sampling error rather than a defect — see 1a.15.*

- [x] 1a.2 **Randomize with locks is not built** (`scene-presets`). No randomize command, no lock switches. The spec's design reasoning is sound and worth keeping — why the command and its locks live in one section rather than the sticky footer — so what is missing is the building, not the deciding. *Built: one Randomize section holding the press and four locks — field, palette, engine, motion — with the values drawn inside the ranges the schema declares rather than a table beside the planner, colours drawn in HSL because uniform RGB averages to mud, and one press written as one undoable record change. The locks are generated from the same list the planner excludes by, so a lock cannot render for a group the reroll ignores*

- [x] 1a.3 **Decide whether `post-fx-suite` belongs to this product at all.** Five requirements, none built, nothing depending on them. They describe a general creative-coding toolkit — ASCII output, datamosh, scanline tearing — while the studio's treatments are hue, saturation and contrast, which are operations on colour because colour is the subject. **This is a scope decision for the product owner, not something the audit should settle**; it needs scheduling or dropping rather than being left to read as work in progress. *Settled 2026-08-21: split, rather than keep or drop. The file was not one thing — halftone is the printing half of this subject (and line halftone **is** the stripe field, which the spec itself said), palette quantization is a colour operation by definition, and channel split along the stripe axis is misregistration, one of the conditions these techniques exploit. ASCII and ANSI output, datamosh smear, scanline tearing and block displacement are removed rather than left pending, because each treats the frame as data to be disturbed. What remains is scheduled below*

- [x] 1a.3a **Halftone and palette quantization** (`post-fx-suite`, kept by the 1a.3 decision). Dot, line and cross halftone with cell size and angle, where line halftone reuses the shared stripe field rather than reimplementing it, and dot density follows source luminance — the same reading of a source `media-stylization` already performs. Pixelation at a controllable block size with optional quantization to the active palette, which is the same act `color-and-gradient-system` asks for when it requires a gradient to be convertible to a band sequence. *Built as a `Layer Print` section: screen, cell, angle, grain, and quantization. The reuse is real — `studioBandInk` came out of the stripe body and both read through it, so a halftone line gives way exactly where a band does. Grain is applied upstream of the body rather than to its output, which is what makes it a coarse reading rather than a smear*
- [ ] 1a.3b **Channel split and the composition order** (`post-fx-suite`, kept by the 1a.3 decision). Displace the primaries against each other along the current stripe axis with an intensity control, deterministic and with no noise to seed. With it, the documented order for the three: halftone, then quantization, then channel split — the first two decide what the ink is and the last displaces it

- [ ] 1a.4 **Decide whether `shader-editor` is still wanted.** Six requirements, none built. The product went the other way deliberately: source is assembled and copied *out* (`shader-delivery` R55) and never comes back. Editing a hook inside the studio and compiling it onto the canvas is the alternative to that, not a complement — one makes a shader editor, the other an instrument whose output is readable. **Owner's call**

- [ ] 1a.5 **Resolve the conflict between `lamellae-3d` and `viewInteraction: "non-spatial"`.** Eight requirements, none built, and one of them requires `mode: "orbit"` while the app declares `non-spatial` with a reason that is its direct negation. This is not a gap to fill quietly: building it makes a spatial product with a gizmo and model-presentation obligations, which is a different product from the one the other specs describe. Either schedule that or drop the file — leaving it means the specs hold a requirement the app is declared against. **Owner's call**

- [x] 1a.6 **The flow cannot read the apply snapshot, so Restore could not move with the rest.** Everything that decides something moved out of the panel and into the dialog; restore was meant to go too and did not. `stack.applySnapshot` reads as `null` from a React selector inside the dialog while `onPanelAction` sees the same value without trouble — confirmed by instrumenting the dialog and reading the raw target. A restore rendered in the flow would be invisible exactly when an author needs it, so `Previous Stack` stayed as a panel row. Understand why the value does not reach the selector, then finish the move. *Done, and the premise did not survive contact: the dialog reads the snapshot perfectly well. The recorded finding was a conclusion drawn from one instrumented run rather than a property of the runtime, and it outlived whatever made it true — a reminder that a diagnosis is a claim with an expiry date and should be re-run before being built around. Restore now lives in the flow and renders only when a replacement is actually held, which is the thing a permanent panel row cannot do: the old row had to sit there inert most of the time, and its proof asserted that pressing it twice did nothing rather than that there was nothing to press*

- [x] 1a.7 **Video as a layer kind.** Asked for directly: an author should be able to bring in a video as well as an image. Nothing of it exists — the import target is `media.image`, the layer kinds are stripes, gradient and image, and there is no decode, no frame sampling and no binding of a frame as a texture per draw. It is a real capability rather than a control: a video layer has a clock, and this product already has one (the loop), so the two have to agree about which drives which. **Scoped by the owner: a video always plays as an infinite loop, exactly as a GIF does.** So it is sampled by loop position rather than played at its own rate — the layer reads its frame from where the timeline is, which is what makes it export as a loop that closes and what lets two videos at different lengths sit in one composition without either one stuttering at the seam. The open question that remains is what happens when the clip is not the same length as the loop: repeat it, or fit it. *Built: neither — the clip repeats a whole number of times, chosen as the nearest whole number to its natural rate, which closes the seam by construction and keeps the speed error to the distance to the nearest integer. A clip is not a fourth layer kind: a frame of a clip is a picture, so every treatment, engine and source mapping reaches it unchanged. Two import surfaces rather than one, because the runtime routes an import by what the file is and its handler registry is signed. Found and fixed a gap of its own on the way: the export frame was built with an empty media map, so an imported picture drew nothing into an artifact*

- [x] 1a.8 **The renderer does not yield during viewport interaction** (`chromatic-render-core`). It should suspend or coalesce animation work while the canvas is dragged, panned or zoomed, then resume at the correct timeline time without changing play state. Nothing does. This did not matter while nothing animated; the loop makes it real, because a drifting composition now redraws continuously while the viewport is being moved. Half-mitigated already: a composition with no drift is pinned to loop zero and does not redraw at all, so the gap is only for compositions that actually move. *Built: the loop is held at the value the scene last used for the length of a gesture, so the parameters are identical and the renderer sleeps. Play state is never dispatched — freezing what the reader passes leaves the clock running underneath, which is what makes the resume land on the clock rather than on the gesture's end. The gesture is inferred from the runtime's transient viewport writes, compared as a value rather than by identity so an unrelated edit does not read as movement*

- [~] 1a.9 **The palette holds four inks, not eight, and is four controls rather than a collection** (`color-and-gradient-system`). The spec asks for a `collectionActions` collection of 2–8 slots; the app has four fixed `color` controls plus a count capped at 4. Nothing needed a fifth ink yet, so this is unbuilt rather than decided — and the current shape has an oddity worth fixing with it: colours C and D exist as controls even when the slot count says two. *Partly done: the range is 2 to 8 and an ink is offered only once the count reaches it, so the oddity is gone and the capability is there. What was holding it at four was the shader's ramp being a ladder of cases -- one branch per slot count -- which is now a walk over an array. Still open is only the collection shape: cardinality is a slider beside the colours rather than the collection's own plus and minus, which is a refactor of every preset in the library for expression an author cannot see*
- [x] 1a.10 **Interpolation space is a hidden choice** (`color-and-gradient-system`). Compositing happens in linear light and nothing says so or offers an alternative, which is precisely what that requirement exists to prevent: two inks mix to a result the author cannot predict from what they set, because the deciding step is invisible. *Built as `How inks meet`, with three options rather than two: light, screen and perceptual (Oklab). Each is right at a different moment, which is why it is a control rather than a better default. Colours still arrive and leave in linear light, so only the walk between two inks changes — proved by asserting the middle differs across all three while the ends stay identical*

- [x] 1a.11 **A picture is treated but never re-rendered through the engines** (`media-stylization`). The engines recolour an imported image and the treatments apply to it, but nothing reads its luminance to drive stripe width or phase, there is no mapping mode, and no quantization to the palette. That is the whole point of the capability: a source should *become* a field, not merely get coloured. Sampling resolution belongs with it rather than as its own task. *Built: two mappings — band width and band phase — driven by the source's luminance and drawn in the layer's palette, with a granularity and a strength control. Building it surfaced a real bug: an imported layer's record keeps whatever kind it was created as, so the sync was collecting image-only controls against the wrong uniform set and silently dropping them*

- [x] 1a.12 **No SVG copy action** (`export-pipeline`). The spec asks for SVG markup on the clipboard for engine states expressible as vector geometry; what the clipboard carries is assembled GLSL. Worth scoping before building: a stripes layer with no jitter, no taper and no engine is expressible as rectangles, and almost nothing else in the product is — so an SVG action that silently omitted the parts it could not draw would be worse than not having one. *Built with that objection as the design: the action disappears rather than degrading. Two things came out differently from the scoping — it delivers the selected layer rather than the composition, because an applicability gate can only see rendered controls and must not promise anything about layers it cannot see; and jitter and taper are drawn rather than gated, because a predicate cannot read a continuous slider at all and both turn out to be geometry — a displaced rectangle and a quadrilateral*

- [x] 1a.13 **Drift is linear only; there are no eased shapes** (`animation-system`). The spec asks for sine, triangle and periodic-noise LFOs. Most of what it wants is already guaranteed better by whole-cycle drift — periodic motion that cannot break the seam, by construction rather than by quantizing behind the author's back. What is genuinely missing is the *shape*: a viewer currently passes at constant speed and never eases. Build the shape if anyone wants it; do not build the LFO mechanism, which the neighbouring requirement forbids in spirit. *Built as `How it travels`: steady, eased, swing. Every shape lands on a whole number of cycles at the end of the loop, so none can open a seam — which is why it is a shape control and not an oscillator with a rate of its own. The proof samples a quarter into the loop rather than halfway, because an easing curve is symmetric about the midpoint and steady and eased agree there exactly*
- [x] 1a.14 **Jitter noise is not seeded from loop time** (`animation-system`). Unmet in letter and moot today, because jitter does not drift. It stops being moot the moment it does: a field re-scattering every frame instead of travelling is the failure, and the fix is to seed from the declared variation *plus* loop position. *Closed as satisfied in substance, and the literal fix would have been the bug: a seed containing loop position changes every frame, which is the re-scatter. The noise is seeded from the band index and the declared variation, so a band carries its own displacement and drift advances which band is where — there is no time term to reseed from. Now proved: a jittered field drifted half a cycle is identical to the same field with the offset set by hand*

- [x] 1a.15 **A layer at full opacity composites at roughly three-quarters weight.** *Not a defect — my sampling error, chased down and closed the same day it was filed. A single pixel at the canvas centre landed on a band boundary, where a layer's coverage is one half because that is what the seam's antialiasing evaluates to. The layer beneath arrived partially, the two fields genuinely differed, and the difference blend correctly returned light. Reading the darkest pixel in a patch instead gives the near-black the requirement describes. Nothing composites at the wrong weight.*

Proved at two levels — the package's own tests speak JSON-RPC over stdio to the server as a process, and a browser proof assembles every one of the nineteen entries through the package and compiles and links each in a real WebGL2 context, because a string that looks like a shader and a driver that accepts it are different claims*
